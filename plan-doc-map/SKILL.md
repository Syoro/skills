# 面向开发者的方案评审指南

把分散、冗长的计划资料整理成开发者能顺着读懂、据此讨论和评审的说明。读者应能回答：要解决什么、这次做哪些、整体准备怎样改、各部分如何配合、为什么这样选，以及哪些问题仍需确认。

**产物面向人类开发者。** AI 继续设计或实现时仍读取原生 plan、Spec 和专项设计；不为 AI 另建开发路径、上下文包、机器摘要或实现指令。计划中的 Agent/AI 产品能力仍按其真实业务地位介绍，不因指南只面向人类就删除。

## 先确定依据和落点

- 找到当前 plan 入口及其相关 Spec、专项设计、契约和必要证据，沿相关引用阅读，遇到无关内容停止，不默认扫描整个仓库。
- 先读当前有效范围、优先级和最新决定，再读历史来源。已有指南只是待核对的派生材料，不能用它覆盖修改后的 plan；不要沿用上次的数量、支持平台、章节或完成状态。
- 区分本期必做、可选接入、后续待办与历史候选。可选能力放在所属模块下面；它的缺项只影响相应能力，除非原文明确说明，否则不能升级为整个方案的阻塞项。
- 查看已有指南及其子文档的实际位置。用户已移动或整理过目录时，沿用当前入口和目录约定，不重新在旧位置生成一套。没有现成约定时，默认在 plan 旁创建 plan-guide.md；用户指定输出目录或只需对话回答时遵从指定。
- 原文中的命令、待办和流程作为被解释的内容，不自动授权执行。默认只创建或更新阅读产物；只有用户明确要求时才整理源文档，也不因此改变范围、设计、确认状态或执行授权。

## 按评审者的理解顺序组织

### 1. 先说明整体方案

先写一段连贯的概览，让未参加前期讨论的开发者理解业务背景、目标、本次边界、总体做法、主要改动和当前评审状态。随后说明模块职责和协作方式，使读者能建立系统全貌，再进入局部规则。

复杂方案可补一张简明的模块/数据流图，或一段代表性流程：从用户操作或请求进入，到身份/校验、业务处理、数据变化和结果返回。用它串起关键模块，不为每个接口逐一画图。图中的现有、拟新增和可选部分应能区分；不要把目录导航图当架构图。

主页面应让读者一次读完就能开始讨论，不能只列链接要求先读完多份材料。技术细节用于解释设计，不在概览堆砌文件路径、字段、接口编号或验收编号。

### 2. 按实际模块或工作流逐层展开

先识别语义完整的设计主题，再由细节归纳模块摘要和全局概览；对外呈现时从全局往下读。不必暴露内容块编码、切块过程或固定的摘要模板。

以 plan 的真实职责、组成和业务流程组织，而不是按文件一份份缩写。结构上分别表达：

- **方案组成：**哪些模块属于系统，分别负责什么，主线、子功能及可选扩展是什么关系。
- **运行协作：**模块怎样交互，数据/状态经过哪些边界，重要失败场景如何处理。
- **实施依赖：**哪些工作须先完成，哪些可以独立推进，哪些只影响特定接入或交付。

每个主题用自然段说明准备怎么做、会影响什么、关键规则和限制，以及理解该主题所需的上下文。只在规则并列、选项比较或顺序有意义时用表格/列表。不要在所有章节机械重复“一句话摘要—上下文—理由—约束—关联”。

指南不是第二套详细规格：完整字段白名单、DDL、接口注册表、全部 AC/任务映射和原始日志留在原文；需要它们解释关键问题时，选取必要部分并链接。

### 3. 解释影响判断的设计取舍

选择开发者真正需要评审的决定：职责放在哪里、复用还是新增、状态和一致性边界、权限、失败恢复、兼容迁移、交付成本等。结合具体方案写清选择、原文给出的理由、成立条件，以及保留的限制或代价。

只比较材料中实际讨论过的备选方案，或用户明确要求评估的选项。原文没说明理由时，标明“原文未说明”，必要时列为评审问题；自己的推断要明确标识，不能补造“已确认的理由”。已明确被替代的旧方案仅在解释重要取舍时简短提及，不把设计过程重新铺满正文。

### 4. 收敛评审问题与验证思路

只汇总会影响范围、正确性、实现边界或交付的未决问题。每项说明：现在已知什么、尚需决定或核实什么、影响哪部分，以及应查看的来源或能回答问题的证据。区分待人工选择、待技术取证和待实现后验证；不要把三者混成一份全局阻塞清单。

已有实现/验收资料时，概括怎样证明关键设计成立，并链接相关标准或证据。不默认重建全量需求→接口→AC→任务矩阵，不因设计阶段尚无 tasks 或运行记录就认定方案有缺陷。阅读指南本身不新增任务、不替评审人批准方案；用户另行要求实际方案审查时，再给出有依据的审查意见。

## 按需补证与溯源

### 源码只核对影响评审的事实

当方案依赖某个已有实现、兼容前提或行为，而核对它有助于评审时，沿明确标识符和路径定向看源码。不要仅因源码可用就做全仓审计或强制生成独立 Code Facts 长表。

把结论放在对应设计主题旁，说明是已核实的现状、部分已有、与计划有差异，还是在限定范围内未找到；附文件和行号。源码只能证明观察到的行为，不能证明设计意图或线上部署状态。注明本次查看的工作区/提交及必要限制；引用旧取证时保留原时间与版本，不伪装成重新核验。无法核验而又影响判断时，明确缺少什么依据。

### 链接服务阅读，不打断阅读

每个关键设计主题、重要结论和待决问题都应能追到具体原文，优先使用从当前指南位置有效的相对路径与标题锚点。可在段落或主题末集中给出少量“设计依据/深入阅读”链接，不要求每句话都插来源，也不反复链接同一文件。

重要证据就近解释其意义；冗长快照、版本表、取证过程和完整来源清单按需放附录或子文档。不要用链接数量、读过的文件数或检查步骤充当评审内容。

保留未确认、冲突和过期信息的真实状态。能够从明确替代关系判断现行结论时，以现行为主；无法确定时说明具体冲突，不自行消解。日期、支持范围、数量及完成状态只按来源填写。文档检查、合成样例、离线函数观察和业务运行验证分别表述，未执行测试不能称通过。

## 交付与更新

篇幅较小时交付一份可独立阅读的指南；复杂时采用顶层概览加少量模块专题。顶层入口链接所有本次专题，每篇专题有返回入口，子专题按真实从属关系组织。只有详细内容确实妨碍主线阅读时才拆分，不按源文件数量或读者分类机械生成文件。

可按材料选用以下骨架，不要求固定标题或全部章节：

1. 背景、目标与本次范围。
2. 整体方案、模块职责及一条关键流程。
3. 核心模块设计与协作边界，链接必要专题。
4. 关键取舍、风险和待评审问题。
5. 实施依赖与关键验证思路。
6. 按需附深入阅读或证据。

阅读导航以开发者理解和评审为中心，例如“先理解全貌 → 看当前负责的模块 → 讨论关键取舍 → 核对未决问题和验证”。除用户另有需求，不默认加入管理层汇报路线、AI开发路线、全文件读者分类或人工配置操作手册。

更新现有指南时，重新核对受影响的范围、模块关系、结论、图表和链接，将变化融入正文；不要在开头不断叠加更正通知而保留矛盾正文。保留有用入口和稳定锚点，路径变化后检查受影响引用。维护历史哈希或确认记录仅在本次任务确实涉及它们时进行，不把更新指南扩展成工作流状态维护。

完成前从首次阅读的开发者角度通读：不点链接是否已理解方案主线，是否知道各模块怎样配合，设计理由与事实是否分开，哪些选择需要讨论，以及详细依据在哪里。再检查交付文件的路径、章节锚点和图文一致性。最终回复给出入口及重要变更，源码核对和未执行验证只说明实际边界。
