# 开发者方案评审指南

把分散、冗长的计划资料整理成一份从整体到细节、便于开发者理解和评审的说明。重点讲清：做什么、怎样组成和协作、为什么这样设计、还需决定什么。

产物面向人类开发者；AI设计与实现仍读取原生plan、Spec和专项资料，不另建AI开发入口。

## 阅读依据

- 从当前plan和最新有效范围出发，沿相关引用读取Spec、专项设计和必要证据，停止于无关内容，不默认扫描整个仓库。已有指南是待更新的派生材料，不能覆盖新plan。
- 区分本期必做、可选能力、后续待办和历史来源，保留真实从属关系。某项可选能力的缺项只影响该能力，除非来源明确规定，否则不扩大为整体阻塞。
- 默认只创建或更新指南。原文中的命令和待办是被解释的内容，不自动授权执行；只有用户明确要求时才修改或整理源文档。

## 自顶向下展开

先确定全局结构和上层问题，再按需深入资料补足细节。围绕方案本身组织，不逐文件缩写，也不要求读者先读完所有原文。

1. **整体方案：** 说明背景、目标、本次范围、总体做法和当前状态，让读者先建立全貌。
2. **模块协作：** 说明主要模块的职责、从属关系与交互。用一条代表性流程串起输入、处理、状态变化和结果；复杂时配简明架构或数据流图。
3. **关键设计：** 逐模块展开重要行为、边界和设计取舍，解释怎么做、为什么、成立条件及代价。只选影响评审的细节，字段表、DDL和完整接口清单留在原文。
4. **评审问题：** 收敛重要未决事项，说明已知情况、需要决定或补证的内容、影响范围及来源。区分人工选择、技术取证和实现后验证，并概括关键验证思路。

同一层先把职责和关系讲清，再深入下层。方案组成、运行调用和实施先后分别表达，不把阅读目录当架构或依赖图。可选子功能放在所属模块下面，跨模块规则说明关联，不为凑成树而改变真实关系。

正文采用连贯解释，表格用于比较或并列规则，列表用于步骤；不机械套用内容块编号或重复摘要模板。主入口应可独立读懂，详细专题供按需深入，不重复维护整套规格或全量验收/任务矩阵。

## 保留依据，控制细节

- 关键主题、设计结论和待决问题链接到具体原文，优先使用相对路径和标题锚点；在段落或主题末集中放必要链接，避免每句插来源。
- 设计理由只按原文说明，推断明确标识；原文未说明且影响判断时列为问题。现行结论替代历史方案的依据要明确，无法消解的冲突保留，不补造确认、日期或完成状态。
- 只有源码核对能帮助判断关键复用前提时才定向查看，说明观察事实与计划的关系，附文件、行号和版本/工作区。引用旧证据保留其时效，不强制生成独立Code Facts长表或进行全仓审计。
- 区分文档检查、合成样例、离线观察和实际运行验证；未运行不能称通过。指南不替评审人批准方案、不新增任务，也不因设计阶段缺少运行记录就认定方案有缺陷。

## 交付与更新

沿用现有指南及子文档的实际位置；没有既定约定时，在plan旁创建`plan-guide.md`。用户指定位置或只需对话回答时遵从指定。

小型方案一份指南即可；复杂方案采用顶层概览加少量模块专题，入口链接所有专题，专题能返回入口。不要按源文件数量机械拆分，也不默认增加管理汇报、AI阅读路线或操作手册。

更新时以当前plan重核范围、结构和结论，将变化融入正文，不靠不断追加更正段落维持旧内容。保留有用入口和稳定锚点，检查相对链接、图文一致性及确认状态，不扩展为无关工作流维护。

完成前通读：读者是否已理解整体方案、模块怎样配合、关键取舍、待决问题，以及去哪里查依据。最终给出指南入口和重要变更即可。
